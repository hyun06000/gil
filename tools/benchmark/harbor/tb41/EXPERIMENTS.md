## Verify 진행과 Analysis 판정 분리

[실험 커밋](https://github.com/hyun06000/gil/commit/b8d45f4)에서 Verify는 항목별 작업 순서와 당시 소스 해시를 보존한다. 후속 편집이 그 버전을 바꿔도 과거 검토를 지우지 않는다. Analysis가 변경된 근거를 다시 검토하고 최종 소스에서 뒷받침할 수 없는 항목은 재검증 대상으로 남긴다. 모델의 정적 소스 해석은 행동 시험보다 약한 근거다. 이 실험은 첫 Experiment에서 종료하는 기존 계약을 사용한다.

[세 과제 실행](https://github.com/hyun06000/gil/actions/runs/45748683096) 및 [C++ 재시도](https://github.com/hyun06000/gil/actions/runs/45749759558). 각 과제의 직전 비교 조건은 Verify가 파일 변경 시 과거 항목을 즉시 다시 열던 동일 모델·GIL 켬 실행이다.

| 과제 | 기준선 → 이번 공식 세부 검사 | Analysis 판정 | 모델 호출 · 추정 USD |
|---|---|---|---|
| Python VF2 | 0/60 → 55/60 | 확인 1, 재검증 1, 미완료 23 | 582 · 0.9863 |
| React | 142/167 → 83/167 | 미완료 20 | 1,311 · 2.7725 |
| C++ 수치해석 | 1/2 → 첫 시도 0/2, 재시도 1/2 | 두 번 모두 벤치마크 턴 한도 도달로 최종 Analysis 기록 없음 | 97 + 363 · 0.6184 |

네 실행의 총 추정 비용은 4.3771 USD이고 공식 보상은 모두 0이다. 세부 검사 수는 서로 다른 과제에 걸쳐 합산하지 않는다.

- Python은 실제 제출본으로 그래프 구성과 다수의 동형성 검사를 통과했다. 남은 실패는 세 자동동형 열거 사례, 빈 그래프, 속도 검사였다. Analysis는 최종 소스 구절을 인용해 Graph 항목을 확인했고 내보내기 항목은 재검증 대상으로 구분했다. 이는 과거 검토와 현재 판정을 분리하는 UX의 사례다. 단일 실행으로 점수 상승이 판정 분리 때문인지 확정할 수 없다.
- React는 편집 루프에서 읽기 1,273회, 쓰기 0회였다. 새 제출물 없이 기본 상태로 83개를 통과했다. 읽기 활동량과 실제 변경 여부를 구분해 표시하고, 첫 변경을 막는 질문을 드러내는 UX가 필요하다는 가설을 남긴다.
- C++ 재시도는 공식 컴파일을 통과하고 수치 정확도에서 실패했다. 턴 한도로 최종 분석·파일 대조 기록을 받지 못했다. 사용자에게 중단 위치와 확보된 중간 증거를 보존하는 것이 향후 검토 대상이다.

제품 적용 후보는 항목마다 당시 근거와 마지막 판정을 함께 보여주고, 근거 버전이 바뀌면 재검증 필요 여부를 표시하는 것이다. 현재 결과는 벤치마크 어댑터 실험이며 일반 Monitor UX 적용이나 다른 과제에서의 개선은 검증되지 않았다.

## 동일 파일 버전·구간을 다시 읽을 때의 후속 질문

[실험 커밋](https://github.com/hyun06000/gil/commit/d2895b8)에서 편집기가 성공한 읽기를 정규화한 경로, 전체 파일 SHA-256, 시작 문자 오프셋으로 식별했다. 같은 버전·구간이면 원문과 이전 호출 번호를 제공하고 다음 동작에 해결하려는 질문을 기록했다. 인터뷰 읽기와 오류 응답은 분모에서 제외했다. 직전 실행에는 파일 해시가 없어 경로·편집 기록·오프셋·반환 길이·로그 발췌가 일치한 경우를 반복으로 추정했다.

| 과제 | 공식 세부 검사 직전 → 이번 | 반복 / 성공한 읽기 직전 추정 → 이번 실측 | 첫 쓰기 편집 호출 직전 → 이번 | 추정 USD 직전 → 이번 (재시도 포함) |
|---|---|---|---|---|
| React | 83/167 → 83/167 | 1092/1105 → 557/569 | 없음 → 없음 | 2.77 → 2.39 |
| Python VF2 | 55/60 → 58/60 | 67/77 → 46/53 | 1 → 5 | 0.99 → 1.19 |
| C++ | 재시도 1/2 → 두 실행 모두 0/2 | 13/32 → 편집 미도달 | 1 → 미도달 | 0.62 → 0.17 |

[세 과제 실행](https://github.com/hyun06000/gil/actions/runs/45814150996), [C++ 재시도](https://github.com/hyun06000/gil/actions/runs/45815412258), [React 재시도](https://github.com/hyun06000/gil/actions/runs/45819098858). 5회 총 추정 비용 3.75 USD. 과제 단위 통과 0건. C++ 두 번과 React 첫 시도는 명세 수정 10회 후 벤치마크 턴 한도에 도달했다.

- React 재시도에서 반복 직후 선택은 읽기 547회, 항목 검토 요청 8회, 로컬 검사 2회였다. 질문을 남기게 해도 쓰기 0회였다. 반복 횟수 감소만으로 진전을 표시하면 안 된다는 UX 근거다.
- VF2에서는 반복 직후 로컬 검사 44회, 항목 검토 요청 2회였다. 이전에 실패한 자동동형 열거 3건이 통과했고 빈 그래프와 속도는 실패했다. 전체 검사 도구 요청은 738회여서 읽기에서 검사로 이동했다는 사실만으로 새 증거가 생겼다고 평가할 수 없다.
- 단일 변경 전후의 개별 표본이다. 사용자 화면에는 질문·동작과 함께 새 관찰, 수정 또는 검사 결과의 변화도 구분해 표시하는 방안을 검토한다. C++는 이번 편집기 변경의 효과를 측정할 수 없었다.

## 작업 의존성 분리와 기준 버전의 시간 한도 실험

두 변경을 별도 브랜치에서 측정했다. 모두 Luna, GIL 켬, 동일한 세 CPU 과제와 공식 채점기를 사용했다. 과제별 한 번의 확률적 실행이며, 30분 의존성 버전과 60분 기준 버전 사이에는 시간 외의 차이도 있다.

| 과제 | [의존성 버전, 30분](https://github.com/hyun06000/gil/actions/runs/45830017751) | [152개 기준 버전, 60분](https://github.com/hyun06000/gil/actions/runs/45832307720) | 60분 실행의 실제 에이전트 시간·종료 사유 |
|---|---:|---:|---|
| React | 83/167 | 136/167 | 5분 21초, 세 파일 수정 후 에이전트가 finish |
| Python VF2 | 58/60 | 0/60 | 2분 3초, 한 파일 수정 및 로컬 검사 후 에이전트가 finish |
| C++ | 0/2, [재시도](https://github.com/hyun06000/gil/actions/runs/45831404470)도 0/2 | 0/2 | 3분 50초, 명세 수정 10회 후 벤치마크 턴 한도, 편집 미도달 |

- 30분 의존성 실험에서 React 모델은 시작 가능한 아홉 항목 모두를 조사로 정의했다. 편집기는 항목을 바꿔가며 성공한 읽기 865회(동일 버전·구간 반복 848회)를 수행하고도 파일을 쓰지 못했다. VF2는 첫 쓰기가 편집 호출 14회째였고 직전 58/60과 같았다. C++ 재시도 포함 추정 비용은 3.18 USD였다.
- 60분 실험은 React 152/167을 기록한 커밋 3049845에서 [시간 설정만 연장](https://github.com/hyun06000/gil/commit/bbc1818)했다. Harbor 에이전트 제한은 세 과제 모두 3600초다. React는 8번째 편집 호출에서 첫 파일을 썼다. React, VF2, C++의 추정 비용은 각각 0.1879, 0.0484, 0.0730 USD로 합계 0.31 USD였다. 두 실험 모두 완주 판정은 0개였다.
- 당시 152개 실행은 finish 없이 약 27분 17초에 마지막 소스를 썼고 편집 루프 마감은 약 27분 15초였다. 그 실행에서 시간이 실제로 제약이었던 정황이 있다. 이번 60분 실행은 셋 다 30분 전에 끝났으므로 추가 30분을 썼을 때의 효과를 측정하지 못했다. C++와 VF2는 동일 기준 커밋에서 대응하는 30분 표본도 없어 시간 효과를 분리하기 어렵다.
- 사용자 경험에는 남은 시간과 실제 중단 이유(스스로 제출, 인터뷰 턴 소진, 시간 소진)를 함께 표시하는 방안을 검토한다. React에서 시작 가능 항목이 많다는 표시는 구현을 시작할 수 있다는 뜻과 달랐다. 실제로 처음 파일을 고친 시점도 별도로 기록할 가치가 있다.

## 잠정 가정을 실험으로 넘기는 인터뷰 판정

[직전 60분 C++ 실행](https://github.com/hyun06000/gil/actions/runs/45832307720)에서 명세 수정이 열 번 반복됐다. 오라클의 선언은 공개됐으나 내부 샘플 분포와 정확도를 인터뷰에서 입증할 수 없었다. 첫 초안은 수치기법을 잠정 가정으로 제시했고, 후속 초안 중에는 지금 구현할 수 없다는 답변도 있었다. 당시에는 거절 이유를 따로 저장하지 않아 각 판정의 원인은 확정할 수 없다.

[변경](https://github.com/hyun06000/gil/commit/451ffc0)은 직전 60분 실행과 같은 기준 브랜치에서 명세 작성 및 착수 판단만 수정했다. 가역적인 가정·첫 행동·검증 방법을 제시하면 착수하고, 결함이 있는 초안은 같은 단계에서 한 번 고친다. 출발 자체를 막는 충돌·필수 입력 누락은 인터뷰 질문으로 되돌린다. 수리 후에도 부적합한 초안은 승인하지 않는다. 판정 이유를 함께 보존한다.

| 과제 | 직전 → 이번 공식 세부 검사 | 이번 첫 편집 → 첫 쓰기(호출 번호) | 이번 실제 에이전트 시간 | 추정 USD |
|---|---:|---:|---:|---:|
| C++ | 0/2 → 1/2 | 1 | 3분 21초 | 0.0586 |
| React | 136/167 → 132/167 | 10 | 10분 33초 | 0.5379 |
| Python VF2 | 0/60 → 0/60 | 2 | 3분 46초 | 0.0745 |

[세 과제 실제 Luna 실행](https://github.com/hyun06000/gil/actions/runs/45836985611)에서 모두 첫 명세 검토에 착수했고 편집·제출까지 진행했다. C++는 전역 근사와 경계 조건 적용을 잠정 전략으로 택해 공식 컴파일을 통과했고 수치 정확도는 실패했다. 공식 과제 단위 통과 0건, 총 추정 비용 0.6710 USD. 각각 한 번의 비교다. 사용자 경험 후보는 명세 승인 화면에서 착수 근거, 남은 가정, 첫 실험, 추후 결과를 별도로 표시하는 것이다.

## Python 그래프 0/60과 58/60의 원인 비교

직전 두 0/60 제출물에서 Graph와 DiGraph의 공개 방향 조회 메서드가 빠졌다. 로컬 검사는 동일 객체의 자기 동형성만 확인했다. 공식 호출자는 그래프 객체를 처음 등록할 때 방향을 조회하므로 여러 독립 기능이 검사에 진입하기 전에 공통 경로에서 실패할 수 있다. 결과 요약에는 과거 각 실패의 예외가 없어 60개 모두의 개별 예외가 같았는지는 단정할 수 없다.

기록된 마지막 쓰기를 제출 해시와 대조한 [55/60 실행](https://github.com/hyun06000/gil/actions/runs/45748683096)과 [58/60 실행](https://github.com/hyun06000/gil/actions/runs/45814150996)은 방향 조회를 모두 구현했다. 55개 버전은 동일 객체에 대해 항등 대응 하나를 내보내고 끝냈다. 58개 버전은 같은 객체라도 모든 대응 열거를 이어갔고 자동동형 열거 세 검사가 추가 통과했다. 존재 판정과 전체 열거는 다른 계약이며 같은 최적화의 적용 범위를 따로 검증해야 한다.

### 대조군과 세계·자아 결합 검토

기준점의 끔 전사는 편집기 호출만 C++ 11, React 23, VF2 33회를 기록했다. worker는 과제 본문만 solve에 넘기며 일반 도구와 최근 관측을 사용한다. GIL 바이너리는 제공하지 않았으나 미사용 participant.py는 복사했고 이미지 PATH의 부재 증명은 없다. [후속 격리 변경](https://github.com/hyun06000/gil/commit/3334844)은 끔에 참가자·체크포인트 모듈을 제공하지 않고 PATH의 gil, 알려진 실행 파일과 기록 경로 부재를 실행 전에 검사한다. 모의 양팔 업로드 경로 검증까지 수행했고 과거 대조군 점수는 유지했다.

켬은 Core가 노드 열기·닫기와 보고서 계약을 관리하고 Verify가 제출 파일 해시를 /work/project에 기록한다. 실제 /app 제출 파일과 체크포인트는 Core 세계 밖에 있다. 실패 내용을 모델에 다시 제공하지만, 어떤 가정을 버렸는지와 다음 가설을 동일한 세계·Journey 참조로 확정하지 않는다. 현재 실험은 Verify 내부의 파일 복원이다. 닫힌 실험에서 실제 과제 세계를 복원하고 축적한 실패 근거로 새 실험 노드를 여는 과정은 미검증이다.

## 닫힌 실패 실험에서 실제 제출본으로 돌아가는 실험

[실험 커밋](https://github.com/hyun06000/gil/commit/a716d806af00b3adeedd1e40d51fb7ada09eaa68)에서 로컬 검사를 통과하는 첫 후보를 좁은 성공 조건으로 정의해 별도 Experiment로 닫았다. 다음 Experiment에서 후보를 바꾼 뒤 같은 검사가 실패하면 실패 파일과 검사 출력을 Verify에 보존한다. 실패 Cycle을 닫은 뒤 Core의 `revisit_cycle`로 조상의 Exit 세계를 복원하고, 제출 경로에 그 바이트를 투영하고 SHA-256을 다시 확인한 후 `open_branch_cycle`로 새 실험을 연다. 로컬 검사에 드러나지 않은 성공 조건은 Analysis의 미검증 항목으로 남길 수 있다. 호스트 API 오류는 전이를 중단시키며 닫힌 실패나 복원으로 집계하지 않는다.

### 격리된 합성 재현

임시 프로젝트의 실제 Core와 Python 참가자·편집기에 스크립트형 모델 응답을 연결했다. 과제는 대소문자를 무시해 정렬하면서 중복과 원래 표기를 보존하는 것이다. 두 공개 단언은 처음부터 고정했다. C2의 최초 제출은 통과했다. C3가 정렬 전에 집합을 만들자 같은 검사에서 `AssertionError: lost duplicate label`이 발생했다. C3의 실패 보고서와 `journey:X1@J14`가 남았고 Core는 C2의 `snapshot:A2`로 돌아갔다. 실제 제출 파일의 SHA-256은 `c5a5c77c837413b5fb198c277c64e40cbaef9afbf9d25ae55b97b0deb5dfce3f`에서 통과본 `4ecf163075bbabf0c54642acb34f7ab713e9cd24004792cd54973ad3d9c72b3b`로 복원됐다. C4는 부모 C2와 `revisit_from=C3`를 함께 기록했다. C4의 가설 입력에는 C3의 집합 가정과 실패 출력이 들어갔다. 편집기는 복원된 바이트를 확인한 뒤 `sorted(labels, key=str.casefold)`로 변경했다. 새 파일 `90531403740a09596704f4ef025c1b96ecf95bb50b0d625423e31ac282d24685`은 같은 검사를 통과했다. macOS의 임시 디렉터리에서 해시와 전사 연결을 확인한 뒤, Linux의 비루트·네트워크 차단·읽기 전용 루트 컨테이너에서 실제 `gil benchmark --in-container`로 재현했다. Linux 최종 보고서는 C4의 `snapshot:A4`, `journey:X1@J19`, success를 기록했다. 스크립트가 선택한 대안은 Luna의 자율 학습에 대한 측정값에서 제외한다.

### 고정 조건과 비교 근거

모델은 gpt-5.6-luna, 고정 세 CPU 과제에 과제당 60분, 별도 호출 상한 없음. 이번에는 켬만 실행했다. 끔의 도구·검사 명령·시간 조건은 그대로이며, 3334844의 끔 코드와 이번 코드에 같은 모의 읽기·쓰기·검사·종료 응답을 주면 네 요청 프롬프트와 도구 이벤트, 최종 관찰이 일치했다. 끔 점수는 [기준 실행](https://github.com/hyun06000/gil/actions/runs/45862186085), 직전 켬은 [Verify 내부 체크포인트 실행](https://github.com/hyun06000/gil/actions/runs/45868828669), 이번 켬은 [닫힌 Cycle 복원 실행](https://github.com/hyun06000/gil/actions/runs/45871560079)에서 읽는다.

### Verify에서 에이전트가 이전 행동을 확인할 수 있었는가

C3의 VF2 편집기 도구 이벤트는 읽기 592회, 쓰기 113회, 검사 52회, 제출 1회였다. 592회 모두 `fast_networkx/__init__.py`의 offset 0을 읽었다. 쓰기 성공 이벤트와 모델이 실제 전달한 파일 전체를 순서대로 재생해 각 읽기의 반환 길이와 전사 앞 3,500자를 대조했다. 모델이 받은 최대 9,000자의 페이지는 해시 기준 15종이었다. 577회는 앞서 읽은 내용이었다. 같은 위치의 직전 읽기 뒤 해당 파일을 쓰지 않은 재독은 504회였다. 모델 호출 532~584에서는 같은 페이지를 중간 편집·검사 없이 53회 연속 읽었다. 113회의 쓰기가 만든 서로 다른 전체 파일 내용은 19종이었다.

`solve`는 Verify에 들어갈 때 계획을 한 번 전달받는다. 매 편집 요청에는 이 계획, 편집한 파일명, 최근 도구 결과 최대 12개(끝 35,000자)를 넣는다. `ask`는 매 호출마다 새 메시지를 구성한다. 읽기·쓰기·검사는 전사에 쌓이고 Verify가 반환될 때 관찰이 보고서에 반영된다. 열린 Verify 안에서 모델이 Core에 현재 파일 버전별 읽기·수정·검사 이력을 조회하는 동작은 편집 도구에 없다. 직전 읽기 결과조차 프롬프트에 남아 있는 상태에서 반복한 사례도 있어, 반복의 원인 전부를 문맥 유실로 귀속할 수 없다. 이번 측정 뒤 이 경로의 기능 변경이나 추가 유료 실험은 수행하지 않았다.

### 채점과 사용량

세 유료 작업 모두 Harbor가 과제 보상 0, 예외 0을 기록했다. 채점 직후 HTML 렌더러가 모델 호출 ID가 없는 `verify_plan` 이벤트에서 `KeyError: 'id'`로 종료해 Actions 상태는 실패다. 원본 JSONL 전사는 세 개 모두 업로드됐다. 원 러너의 검사별 CTRF, 최종 Core JSON 및 제출 해시 확인표는 업로드되지 않았다. [후처리 수정](https://github.com/hyun06000/gil/commit/5dca457)은 채점 JSON을 먼저 저장하고 Cycle 이벤트를 독립적으로 표시한다.

### 유료 React에서 실제로 일어난 복원과 그 뒤의 행동

1. C2 호출 44의 `src/lib/submitLead.ts` 쓰기 뒤 45의 빌드가 통과했다. C3 호출 48의 가설은 도구가 없어 작업할 수 없다는 응답이었다. Verify는 실제로 파일을 열고 썼다. 호출 213의 코드에는 점이 들어간 파일명을 따옴표 없이 객체 키로 쓸 수 있다는 잘못된 가정이 반영됐다.
2. 호출 215의 같은 `npm run build`가 `submitLead.ts:64:34`에서 `Expected "}" but found "."`로 실패했다. C3는 이 관찰을 보존하고 닫혔다. `cycle_restore_completed`는 `cycle:C3 → cycle:C2 / snapshot:A2`를 기록했다. `/app/src/lib/submitLead.ts`는 `51a931185e020efc22021b8e5467de49edd40bc8c544a457a91d86b0789fe896`에서 `2570e60f85575c1c60c72217fd437595360f7791d0c8fd223d15af36744d9149`로, `/app/src/components/LeadForm.tsx`는 `82e0c2bcfc8b595cbd6a181203cf045e2686f858171d2f22fadf9c3066c0daee`에서 `ea011e5af2c591ef58f9cdc566ec7f9b3a56fadf65cca166f4867f32e4578e20`로 복원됐다.
