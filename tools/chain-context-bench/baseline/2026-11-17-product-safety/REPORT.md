# Chain context 제품 구성 기준선 — 2026-11-17 (`product-safety`)

[`tools/chain-context-bench`](../../README.md)를 제품 구성(`approved-plan,visual-authoring,product-safety`)의 실제 Core로 실행한
첫 기록이다. [`baseline/2026-11-17`](../2026-11-17/REPORT.md)는 보호 기능이 없는 개발 구성의 기록이며 그대로 둔다.
이 폴더는 그 기록을 고치거나 대체하지 않는다.

크기는 바이트(B)·코드 포인트이며 **토큰 수가 아니다.** 모델을 호출하지 않았으므로 모델 입력량·전체 실행 비용·
재조회·작업 정확성에 대해서는 아무것도 주장하지 않는다. 임계값·CI 기준도 만들지 않는다.

같은 폴더의 [`bench.md`](bench.md)는 도구가 생성한 전체 표, [`summary.json`](summary.json)은 `compare` 입력용 축약본이다.
읽기 호출의 응답 원문(`recordings/`)과 큰 `bench.json`은 저장소에 넣지 않았다.

## 보완한 측정 공백

이전 도구는 실패한 Experiment 뒤에 `gil_revisit`을 직접 호출했다. 제품 구성은 모델의 그 호출을 거절하고 Monitor 승인을
요구하므로 누적 실패 사례(`failures` 1·2)가 `unsupported`로 기록됐다. 제품에 복구 기능이 없는 것이 아니라 도구가 기존
승인 복구 경로를 밟지 못한 것이다. 같은 실행 파일로 이전 도구를 실행해 그 상태를 먼저 재현했다
(`failures=1,2` → `unsupported`, 거절 1회).

이번 실행은 Core가 도구 목록에 내놓은 App 전용 `gil_revisit_review` → `gil_revisit_apply`를 밟았다
([M4-R](../../../../spec/GIL_Revisit_Recovery_v0.1.md), [상태별 재개 기준선 시험](../../../chain-resume-benchmark/README.md)과 같은 계약).
보호 기능을 끄거나 거절 조건을 완화하지 않았고 `src/`·`tests/`는 고치지 않았다.

**승인은 시험 harness가 넣은 합성 입력이다.** Core가 돌려준 계획의 digest와 비공개 승인 정보를 그대로 되돌려 보냈을 뿐
사람이 Monitor 버튼을 누르지 않았다. 결과는 합성 승인 6회·사람의 승인 0회로 적는다. Core는 App 전용 도구로 들어온
승인을 `monitor_button`으로 적는데(6건), 이 실행에서 그 값은 사람 클릭의 증거가 아니다. 승인 정보는 결과·기록 파일에 없다.

  --before tools/chain-context-bench/baseline/2026-11-17-product-safety/summary.json --after <새 폴더>/summary.json

## 보존 점검 — 실패 0·1·2회

새 Core 프로세스의 읽기 응답과 생성한 사례가 아는 사실을 맞춰 봤다. 반복 2회 모두 같다. 위반 0건.

| 실패 | 실패 Cycle 참조 | 실패 투영 표식 | 실패 Cycle 절 | 현재 항목·Cycle | 실행 연결(같은 항목) | 연결이 `gil_context`에 | 보존 폴더 | 원본 bytes 일치 | 읽기 전후 동일 |
|---|---|---|---|---|---|---|---|---|---|
| 0 | 0/0 | 0/0 | 없음(기대대로) | `I1`@`cycle:C2` | 1/1 | 1/1 | — | — | 예 |
| 1 | 1/1 | 4/4 | 있음 | `I1`@`cycle:C3` | 2/2 | 2/2 | 1/1 | 4/4 | 예 |
| 2 | 2/2 | 8/8 | 있음 | `I1`@`cycle:C4` | 3/3 | 3/3 | 2/2 | 8/8 | 예 |

- **실패 근거**: 실패한 Cycle마다 그 참조와 투영 표식 네 개(Define 목적·판정의 교훈·인계·revisit 이유)가 `gil_context`에 있다.
  실패 Cycle의 내부 Step 표식 12개는 어느 읽기 호출에도 없다(Cycle 해상도). 실패 0회 사례에는 실패 절이 없다.
- **현재 항목**: `gil_plan_read`의 현재 항목과 현재 Cycle이 생성한 사례와 같고, 이번 Experiment의 승인 항목이 `gil_context`에 있다.
- **재시도 연결**: `gil_plan_read.executed_cycles`에 실패한 시도와 현재 시도가 모두 같은 항목 `I1`로 남아 있고, 같은 참조가
  `gil_context`에도 있다. `gil_status`는 실패 1·2회 사례에서 마지막 실패 Cycle을 가리켰다(관측만, 판정 대상 아님).
- **복구가 남긴 보존본**: 복구마다 `approval.json`·`files.json`·`source.json`이 있고 저장된 승인이 그 실패·대상 Cycle을 가리킨다.
  보존된 원본 4개(복구당)의 bytes가 `files.json`의 SHA-256과 같다. 복구 계획은 매번 변경 2건(둘 다 원본 보존 후 제외)이었다.
  저장 레코드 어디에도 승인 정보가 없다.
- **불변성**: 읽기 전후 프로젝트·설정·실제 저장 레코드 폴더(보존본 포함)의 전체 digest가 26개 실행 모두 같다.

점검은 참조·표식의 존재와 구조 필드의 일치만 본다. 요약의 의미 보존, 복원된 파일 내용의 의미는 판정하지 않았다.

## 보호 없는 구성과의 관계

- **같은 소스에서 두 구성의 읽기 응답이 같았다.** 같은 커밋 `dceaac8`에서 `approved-plan,visual-authoring`로 빌드한 실행 파일
  (sha256 `721e21d1…bf2613`, tools 31개, 복구는 `gil_revisit` 6회)을 같은 도구로 실행해 `compare`했다. 13개 사례의 세 읽기 호출
  모두 text·structured 크기 차이 0, 내용(Monitor scope id만 정규화) 동일. 누적 실패 사례도 같다. 이 비교는 이 13개 자리와
  세 읽기 호출에 한정되며, 두 구성의 다른 응답(복구 거절 안내 등)이 같다는 뜻이 아니다. 그 실행 결과는 저장소에 넣지 않았다.
- **도구 변경은 보호 없는 구성의 측정을 바꾸지 않았다.** 변경 전 도구와 변경 후 도구를 같은 실행 파일로 실행한
  실패 0·2회 사례의 크기·내용이 같다.
- **과거 기준선과 숫자가 다른 것은 소스 차이다.** `baseline/2026-11-17`은 source `bcefbc4`이고 이번은 `c2b94eb` 이후다.
  기준점 `gil_context` text가 6230 B → 6830 B, `gil_plan_read`가 3350 B → 3652 B로 다르다. 이 차이의 원인은 이번에
  분석하지 않았다. 과거 기준선과 이 기록을 개선 전후로 비교하지 않는다(`compare`는 기능 조합 차이를 표시한다).

## 재현성

- 같은 실행 안 2회 반복: 13개 사례 모두 세 호출의 text·structured 크기와 내용이 같았다.
- 별도 실행 2회(이 기준선 포함): `compare` 결과 조건 차이 없음, 같은 실행 파일, 13개 사례 모두 크기·내용 차이 0.
- 자체시험 27개 통과(그중 2개는 실제 Core: 보호 없는 구성과 제품 구성 각각 실패 0·1·2회 × 2회 반복).
- 소요 시간·`.gil` 바이트는 기록했지만 시간은 재현 대상이 아니다.

## 확인하지 않은 것

- **Windows.** 이 기록은 macOS arm64 한 대의 실행이다. Windows의 승인 복구는 별도 핸들 기반 구현과 외부 저장 위치를 쓰며,
  이 도구를 Windows에서 실행하지 않았다. Mac 결과를 Windows 실행 성공으로 읽지 않는다.
- **사람의 승인과 화면.** 합성 승인이다. Monitor의 변경 목록 표시, 사람의 확인, 실제 Host 버튼, 복구 뒤 채팅 이어가기는 보지 않았다.
- **토큰·비용·정확성.** 바이트·문자 수이며 토큰 수가 아니다. Host의 모델 입력 구성, 재조회, 작업 정확성은 측정하지 않았다.
- **다른 복구 모양.** 닫힌 실패 Cycle에서 같은 분기점으로 돌아가는 경우만 만들었다. 보호 경로 차이·미기록 변경 거절, 중단 뒤 재개,
  더 먼 조상으로의 복구, 실패가 3회 이상이거나 다른 축과 겹친 경우는 측정하지 않았다(도구 상한은 실패 8회).
- **자동 승인 구성.** `recovery-auto-approval` 빌드와 그 자동 승인 진입은 실행하지 않았다.
- **다른 언어·읽기 호출.** `ko-KR`과 세 읽기 호출만 측정했다(`gil_story`·`gil_help` 제외).
- **자동 검사 연결.** 제품 구성 실제 Core 시험(`CHAIN_CONTEXT_BENCH_GIL_PRODUCT`)은 로컬에서만 실행했다. 자동 검사 설정은 고치지 않았다.
