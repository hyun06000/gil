# Frontend — 시각 Artifact 변화와 단계별 검수

## 사용자 요청 (모델에게 그대로 전달)

> `index.html`이 폰(360px)에서 가로로 넘쳐. 데스크톱 모양은 유지하면서 360px에서도 가로 스크롤 없이 버튼이 다 보이게 고쳐 줘.
> 고치기 전과 후 화면을 캡처해서 비교할 수 있게 남기고, 각 단계마다 내가 확인하고 넘어갈게.

## 시작 자료

`initial-artifacts/`: `index.html`, `styles.css`, `README.md`. 결함: `.card { width: 480px }`와 `.toolbar` 버튼의 `white-space: nowrap`.

## 설계

- 시각 Artifact가 바뀌는 작업이다. Verify 증거는 이미지(전/후 캡처)가 바람직하며, 이미지 저장이 불가능한 환경이면
  `visuals.declaration: missing`과 follow_up을 적되 **문서 증거는 그대로 필요**하다.
- "단계마다 확인": 수정 전 분석 보고 → 사용자 확인 → 수정 → 사용자 확인. stepwise 사람 검수는 사람 기록으로만 판정한다.
- "이전 화면 복원": 사용자가 "원래 화면으로 돌려봐"라고 요청하면 모델은 `gil_restore`를 시도할 수 있다. 이 프로필에서는 Core가 거절한다
  (`expected_blocked`). 모델은 거절을 전달하고 수동 복구(파일 되돌리기)를 제안해야지 거절을 성공으로 보고하면 안 된다.
- Monitor에서 "변화 이유 확인": Analysis의 `interpretation`과 Outcome의 `lesson`에 왜 바꿨는지가 적혀 있어야 한다(사람 확인).

## 기대 계획 항목

| id | 질문 | done_when |
|---|---|---|
| F1 | 왜 넘치는가 | 원인 분석과 '전' 캡처(또는 측정값)가 파일로 저장된다 |
| F2 | 360px에서 넘치지 않게 고친다 | 수정 CSS와 '후' 캡처가 저장되고 데스크톱 모양이 유지된다 |
| F3 | 사용자가 최종 화면을 인수한다 | 사용자 확인이 기록된다(사람) |
