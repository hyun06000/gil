[언제 읽는가]
  Experiment 를 열어 Define 의 problem 과 success_condition 을 적을 때.
  한 실험이 너무 많은 일을 하거나, 반대로 가치 없는 준비 동작까지 쪼개질 것 같을 때.

[지금 할 일]
  승인된 현재 항목(승인 계획 프로필이면 gil_plan_read 의 current_item)과 인터뷰 기록을 읽는다.
  그 항목과 같은 문제·완료 범위 안에서, 지금 수행하고 결과를 판정할 수 있는 문제 하나를 적는다.
      problem            해결할 질문과 범위 — 확보한 입력, 첫 행동, 멈출 지점이 보이게
      success_condition  같은 문제의 관측 가능한 판정 조건 — 예/아니오를 구분하는 기준이며 조사 완료 자체가 아님
  작업 방법의 가설은 Hypothesis 에, 실제 실행은 Verify 에 둔다. 제안 단계의 실행 순서는 출발점이다.

[현재 구현과 설계 방향]
  현재 승인 계획 프로필은 항목과 실험을 직접 연결한다. 아래 같은 범위 규칙은 그 제품 제약이다.
  새 설계는 안정된 Chain 요구 아래 여러 작은 Define 을 허용하지만 아직 활성화되지 않았다.
  새 Chain 을 여는 것만으로 이 제약을 우회하지 않는다. 과거 승인·완료 기록을 바꾸지 않는다.

[불변식]
  problem 은 반드시 예/아니오로 답할 단일 명제를 물음으로 적는다. 「살펴본다」「확인한다」는
  활동 설명을 문제로 쓰지 않는다. 판정 기준을 미리 고정하고 결과를 본 뒤 질문을 뒤집지 않는다.
  답할 근거가 부족한 상태를 「아니오」로 단정하거나 조사 완료를 명제 충족으로 세지 않는다.
  하나의 구체적인 질문만 갖는다. 따로 성공·실패를 판정할 수 있는 다른 목표는 섞지 않는다.
  필요한 입력·선행 결과·권한이 지금 확보돼 있거나, 바로 그것의 확인이 이번 문제다.
  이번에 얻을 관측 가능한 결과와 완료 판단이 명확하다. 후속 항목까지 끝내야 판정할 수 있으면 다시 나눈다.
  범위와 멈출 지점이 분명하며, 다음 문제는 별도 후보로 남긴다.
  더 나눠도 독립적인 질문·검증 결과가 생기지 않는 준비 동작은 별도 Cycle 로 만들지 않는다.
  「가장 작다」는 문장이 짧거나 파일·명령이 하나라는 뜻이 아니다. 실행 시간·파일 수·단어 수로 크기를 재지 않는다.
  승인된 항목과 Define 은 같은 문제를 가리킨다. 항목의 일부만 수행하고 전체를 완료 처리하지 않는다.
  이미 승인된 항목의 분할·대체·부분 완료 연결은 아직 계약에 없다. 필요하면 그 막힘을 그대로 알리고
  (gil_plan_request_interview 는 요청을 보존한다) 승인 범위·기록·부분 결과를 바꾸지 않는다.
  문제를 좁히는 추론이 새 목표·새 권한·미승인 작업을 더하는 근거가 되지 않는다.

[올바른 예]
  Chain 목표 「매출 자료로 개선안을 만든다」. 현재 항목은 cycle/interview/clarify 의 예에서 승인된 그대로다.
      항목 A  제공된 표의 날짜·금액 열이 월별 집계에 쓸 수 있는가 — done_when: 필요한 날짜·금액 열이 존재하며 모든 대상 행이 합의한 형식·누락 허용 기준을 충족한다
  Define 은 이 항목의 문제와 완료 범위를 좁히거나 넓히지 않고, 확보한 입력(sales.csv)만 구체적으로 적는다.
      problem: 제공된 표 sales.csv 의 날짜·금액 열이 월별 집계에 쓸 수 있는가?
      success_condition: 필요한 날짜·금액 열이 존재하며 sales.csv 의 모든 대상 행이 합의한 형식·누락 허용 기준을 충족한다
  항목 B(꺾인 구간·원인 후보)와 항목 C(개선안 초안)는 이 결과를 받은 뒤의 문제다. 여기서 앞당기지 않는다.

[흔한 실패]
  problem 에 Chain 목표를 그대로 적는다 — 자료 점검·분석·차트·개선안이 한 실험이 된다.
  승인 항목이 크다고 그 일부만 작게 정의해 수행한 뒤 항목 전체를 완료로 적는다.
  파일 열기·폴더 만들기처럼 검증할 결과가 없는 준비까지 실험 하나로 쪼갠다.
  success_condition 을 「개선안이 좋다」처럼 판정할 수 없게 적는다.
