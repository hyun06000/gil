[언제 읽는가]
  Interview 의 Question·Interpretation·Synthesis 자리에서 무엇을 묻고 무엇을 제안할지 정할 때.
  사용자의 요청이 「편리하게」「잘 분석」「전부 자동화」처럼 그대로는 완료 기준이 되지 않을 때.

[지금 할 일]
  Question — 다음 결정에 영향을 주는 미해결 쟁점 하나를 묻는다.
      실제 사용 상황과 입력 · 원하는 결과의 예와 원하지 않는 반례 · 포함/제외 범위 ·
      제약 · 우선순위 · 사용자가 판단할 수 있는 완료 조건
  이미 받은 답은 재사용한다. 이미 충분히 구체적인 요청에는 질문을 더하지 않는다.
  사용자가 방법을 모르면 구체적인 선택지와 차이를 제시한다.

  Interpretation — 세 가지를 갈라 적는다.
      사용자 답으로 확인된 사실 · 에이전트의 해석과 권장안 · 아직 모르는 것
  다음 항목의 실행이나 승인에 중요한 모호성이 남으면 Synthesis 전에 Question 을 다시 연다.

  Synthesis — 짧은 명제로 제안한다.
      합의할 목표 · 이번 범위 · 중요 제약 · 확인할 결정
      실행 항목: 문제 하나 → 기대 결과 → 관측 가능한 완료 판단 (입력·선행 조건·첫 행동·검증 방법은 옆에)
  승인 계획 프로필이면 같은 내용이 draft.scope · draft.items(question/done_when) · draft.synthesis 에 들어간다.
  입력 모양은 그대로다 — 새 필드를 만들지 않는다.

[불변식]
  첫 항목은 현재 자료·권한·범위에서 바로 착수할 수 있어야 한다.
  전제가 불확실하면 그것을 확인하는 작은 항목이 첫 항목이다. 뒤 항목을 실행 가능한 것처럼 확정하지 않는다.
  선행 결과가 필요한 항목은 그 의존을 적고, 결과를 미리 가정하지 않는다.
  한 항목에 독립적인 목표 여러 개를 묶지 않는다. 기능 이름만 나열하지 않는다.
  한 명제에 따로 반대할 수 있는 결정 여러 개를 숨기지 않는다. 중요한 미결 질문은 승인 문구 속에 묻지 않는다.
  명제는 basis_refs 로 실제 Question·Interpretation 참조에 연결한다. 짧게 바꿨다고 합의된 요구가 되지 않는다.
  간결화는 승인 범위·제약·완료 조건·위험·불확실성을 생략하지 않는다. 인터뷰 전문·같은 배경은 반복하지 않는다.
  고정 질문 수, 해결과 무관한 질문, 이미 확인한 요구의 반복은 심층 인터뷰의 근거가 아니다.
  Core 는 자연어의 문제 크기를 판별하지 않는다. 글자 수·질문 수를 채우는 것은 합격이 아니다.

[올바른 예]
  요청 「매출 자료로 개선안을 만들어 줘」
      Question: 어떤 표(열·기간)를 쓰는지, 개선안이 쓰일 자리와 원하지 않는 결과의 예, 이번에 뺄 범위
      항목 A  제공된 표의 날짜·금액 열이 월별 집계에 쓸 수 있는가 — done_when: 필요한 열·형식·누락 여부를 실제 자료로 확인한 기록과 사용 가능 여부·근거가 남는다
      항목 B  (A 의 결과를 받아) 월별 추이에서 매출이 꺾인 구간과 원인 후보 — done_when: 구간과 근거 수치가 저장된다
      항목 C  (B 의 결과를 받아) 개선안 초안 — done_when: 원인 후보별 개선안과 검토 요청 사항이 문서로 남는다

[흔한 실패]
  「자료 점검·원인 분석·차트·개선안 작성」을 항목 하나에 묶는다 — 어느 결과를 보고 끝났다고 할지 없다.
  「편리하게」를 그대로 success_criteria 에 옮긴다 — 사용자가 판단할 수 없다.
  배경 설명이 길어 목표·범위·결정이 묻힌다 — 짧지만 제약을 빠뜨린 제안도 같은 실패다.
  근거 없이 명제만 짧게 쓴다 — basis_refs 가 실제 답변을 가리키지 않으면 합의가 아니다.
